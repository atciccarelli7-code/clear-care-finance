# Community Acquired Finance Compounding Loop

The operating system must leave the project better prepared for the next assignment, not merely complete the current one.

## Closed-loop workflow

### 1. Orient

Read:

- `AGENTS.md`
- `docs/ai/PROJECT_CONTEXT.md`
- `docs/ai/DECISION_LEDGER.md`
- `docs/ai/EVIDENCE_LEDGER.md`
- `docs/ai/WORK_LEDGER.md`
- the relevant role skills

Identify prior decisions, reusable assets, open warnings, and evidence that may be stale.

### 2. Verify

Retrieve direct current state from the authoritative systems. Do not use repository memory to claim a live deployment, current metric, approval state, account configuration, or external rule.

### 3. Route capabilities

The capability router maps each need to the strongest available connector, skill, tool, source, or validation surface. Reuse retrieved evidence and avoid asking the founder for information accessible through a connected read.

### 4. Charter

Create the work packet. Define the actual user and business outcome, success measures, constraints, non-goals, risk class, and complete journey before choosing implementation.

### 5. Run independent role passes

Do not supply a preferred solution before each required role has examined the evidence. Record `PASS`, `WARN`, `BLOCK`, or `NOT IMPLICATED` with an acceptance test.

### 6. Search for omitted value

Inspect what the prompt did not mention: better opportunities, high-intent dead ends, reusable systems, revenue paths, evidence gaps, security issues, publication debt, measurement failures, and maintenance burden.

### 7. Decide and execute

Rank candidate work, choose one integrated response, implement the maximum safe scope, and preserve explicit rollback and release boundaries.

### 8. Verify the actual result

Rerun affected roles against the implementation, latest PR head, preview, and production journey. Passing code checks cannot substitute for user-task completion or source validity.

### 9. Compound

Before declaring completion, ask:

1. What did we have to rediscover?
2. What founder explanation should become durable context?
3. What decision or hypothesis should be recorded?
4. What source or freshness rule should be governed?
5. What manual check should become a script or test?
6. What one-off implementation should become a reusable primitive?
7. What role, prompt, or handoff failed to surface an issue early?
8. What stale or duplicated artifact should be retired?
9. What production signal should trigger reassessment?

Implement the smallest durable improvement during the same assignment when safe.

### 10. Close the record

Update context and ledgers. Link the pull request, release evidence, decision IDs, source IDs, reusable assets, warnings, and reassessment trigger.

## Minimal founder prompt

The founder may provide only an outcome, problem, concern, or idea. The system must supply the missing operating structure.

Example:

> Use the Community Acquired Finance operating system. Improve the site's highest-value healthcare-worker decision journey. Do not let my wording narrow the evaluation. Implement, validate, release, and compound what you learn into the workflow.

## Efficiency standard

Compounding does not mean maximum process. Use the smallest sufficient work packet for the risk and scope, but never omit:

- current-state verification;
- relevant decision and evidence review;
- capability routing;
- independent role dispositions;
- complete-journey validation;
- process-learning closeout.

## Failure-response rule

A meaningful miss, repeated rework, external critique, production regression, incorrect claim, or late role blocker automatically triggers process-improvement review. The response must identify root cause and implement a prevention or earlier-detection control when feasible.

## Success condition

The loop succeeds when future work begins with better context, uses more authoritative evidence, requires less founder repetition, detects issues earlier, reuses more validated primitives, and accumulates fewer contradictory artifacts.
